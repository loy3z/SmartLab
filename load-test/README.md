# Sprint 3：压力测试

测试 SmartLab 在 200 名学生、10 名 Admin 和 2 名 Manager 同时使用时的表现。只用 Python 标准库，不需要安装压测工具。

通过标准：95% 的请求在 1 秒内完成，出错少于 1%；同一时段不能出现重复预约。

## 文件

| 文件 | 作用 |
| --- | --- |
| `stress-ec2.sh` | 总控：在服务器上起临时测试副本，跑压测，出报告，再删除副本 |
| `load.py` | 模拟用户操作，记录每个请求的耗时和结果 |
| `report.py` | 把结果整理成 `summary.md` 和 `chart.html` |
| `profile.py` | 在服务器空闲时测单个请求的耗时和 SQL 条数 |
| `seed.sql` | 压测账号（只用于临时数据库） |
| `fill.sql` | 一学期的历史数据：约 5000 条预约（只用于临时数据库） |

## 怎么运行

在 Git Bash 里运行，服务器上要装好 Docker：

```bash
export EC2_HOST=ubuntu@<服务器地址>
bash load-test/stress-ec2.sh --small
bash load-test/stress-ec2.sh
bash load-test/stress-ec2.sh --profile
```

三条命令分别是试跑（约 5 分钟）、正式规模（约 15 分钟）和单请求测时。其他选项写在 `stress-ec2.sh` 开头。

- 测的是已提交的 `HEAD`；加 `--worktree` 可以测没提交的改动。
- 测试副本是一个独立的 compose 项目：有自己的数据库、随机生成的密码和密钥，邮件关闭，只监听服务器本机。跑完自动删除，不碰线上的容器和数据库。
- 测试期间副本和线上网站共用 CPU，线上会变慢。
- 结果保存在仓库外的 `../output/stress/<时间>/`。

## 三种场景

1. **日常**：所有人同时在线 5 分钟，每人每 5–15 秒操作一次。
2. **高峰**：200 名学生在同一瞬间提交同一时段。
3. **逐步加人**：只读，每人每 1–3 秒操作一次，从 10 人加到 400 人；p95 超过 5 秒或出错超过 5% 就停。

## 结果（t3.small，2 核，带 5000 条历史预约）

| 指标 | 修之前 | 第一轮 | 第二轮 | 第三轮 | 合并 main 后 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 学生首页（单个请求） | 820 ms | 16 ms | 17 ms | 8 ms | 8 ms |
| Booking Records（单个请求） | 9.1 s | 8.2 s | 0.96 s | 0.97 s | 0.95 s |
| 日常中位数 | 未单独记录 | 14.8 s | 2.0 s | 390 ms | 210 ms |
| 日常 p95 | 30 s 超时 | 27.3 s | 4.0 s | 1.8 s | 1.5 s |
| 日常出错 | 98% | 0.45% | 0 | 0 | 0 |
| 高峰 p95 | 30 s 超时 | 8.6 s | 6.2 s | 4.6 s | 4.9 s |
| 逐步加人：p95 < 1 秒的最多人数 | 未测 | 10 | 50 | 100 | 100 |

前四列测于 2026-10-29（最后是 `03c4657`），最后一列测于 2026-11-01（`2cdfc86`，包含后台定时任务和邮件队列）。

- 日常场景的 p95 还没到 1 秒的目标。这时每个接口本身已经很快，请求主要在排队，CPU 平均约 80%。
- 高峰场景的正确性通过：200 个请求全部成功，1 条待审批、199 条候补，没有重复预约。修之前全部超时，无法检查。
- 压测时邮件是关闭的，所以结果不包含发送邮件的开销。第三轮和合并后的差别在正常波动范围内，不能说合并让系统变快了。
